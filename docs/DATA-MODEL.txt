Mibly｜数据模型与种子数据
回答两个动手前要定的问题：① 餐厅和餐食怎么分层、怎么聚合；② 种子数据覆盖哪些场景、保证主链路命中。
代码依据：src/data.ts（users / venues / seedMeals / friendStories）、src/socialGraph.ts、server/recall-service.ts。

一、数据分层

1. 餐食 Meal（最小单位，一条朋友分享）
id、userId（作者）、food / foodZh（标题）、note / noteZh（留言，朋友当时说的话）、date、time、
type：restaurant 餐厅 / homemade 在家做 / delivery 外卖 / other 其他、
venueId（只有 restaurant 才有）、audience：friends 朋友可见 / private 仅自己、photo。

2. 餐厅 Venue（目录实体，与餐食分开）
id、name、area（商圈级区域，如 South Side）、address、cuisine、url。共 9 家，在 venues 目录里维护。
餐食只通过 venueId 指向餐厅，不在餐食里重复存店名和地址。

3. 聚合规则
- 同一家店 = 同一个 venueId。不按店名字符串或坐标去匹配，避免“Kura”和“Kura Revolving Sushi Bar”被拆成两家。
- “找那一餐”返回的是餐食（原帖）。前端把命中的餐食按 venueId 分组：同一家店的多条记录合成一张餐厅卡片，标题是店名，下面列出每位朋友的那条记录和 AI 给的理由；“查看餐厅”“收藏”针对这家店，只出现一次。
- 在家做的饭、外卖、其他类型没有 venueId，每条单独成卡，并显示“在家做的 · 不显示地点”，不补地址。
- 收藏的对象是餐厅（venueId），不是某条餐食。

4. 地点与隐私
- 地图是插画示意，餐厅只到商圈级区域；地图标记表示“分享过的一餐”，不是朋友的实时位置。
- 在家做的饭不生成地图标记，不出现精确住址。
- 发给模型的候选只有：id、作者名、菜名、留言、日期时间、类型、餐厅名/区域/类型。没有照片、地址、坐标、受众标记和好友关系图。

二、权限（服务端执行）

- 默认范围“朋友”：已确认好友（maya、eric、anika、jordan）的 friends 可见记录，不含自己。
- “自己”：本人全部记录，包括 private。“全部”：两者合并。
- 他人的 private 记录、被隐藏的好友、未接受的好友申请（priya）、朋友的朋友，都不会进入候选，也不会发给模型。
- 朋友的记录以服务端的 seedMeals 为准：浏览器只告诉服务端“我正在看哪些记录 ID”，内容由服务端从自己的副本重建，篡改的文字会被覆盖。浏览器只能额外提交“本人在这台设备上新发的记录”。
- 演示没有账号系统，当前用户固定为 daniel。这是演示边界，正式产品需要登录与服务端数据库。
