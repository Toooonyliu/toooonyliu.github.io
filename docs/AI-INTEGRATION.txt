Mibly｜AI 接入说明（浏览器端模型，纯前端）
适用代码：src/recall/adapter.ts、semantic.ts、embedder.ts、tokenizer.ts、engine.ts、RecallPanel.tsx
更新：2026-10-18

1. 为什么是浏览器端

REDcowork 上线只接受纯前端作品（上线 WEB_APP 版本时报错“代码包不是纯前端网站”，题目也写明“仅支持纯前端作品”）。平台大模型只能在服务端通过 guard_sdk/ai 调用，前端不能直连、也不能放密钥。所以核心 AI 改为在用户自己的浏览器里运行。
过程记录：曾在 WEB_APP 预览里接通平台大模型（9 条查询全部正确，平均 3–6 秒），但该形态无法上线，已移除；浏览器端方案是在平台约束下唯一能让核心 AI 真实运行的做法。

2. 模型

bge-small-zh-v1.5（BAAI 中文检索向量模型，512 维），int8 量化 ONNX，约 24 MB；onnxruntime-web 1.27.0（WebAssembly，单线程）。
模型、词表、WASM 运行时都和网页放在同一站点（site/models、site/assets），没有 API key、没有服务端、没有第三方 CDN。用户输入的问题和朋友的记录都不离开设备。
文件来源：ONNX 权重取自 npm 包 dsh-recall-models@0.1.0，词表取自 dsh-recall@0.3.0（与 bert-base-chinese 一致，21128 词）。sha256(model_int8.onnx) = 277740d2…4c25。

3. AI 做什么，代码做什么

AI（向量模型）：理解换了说法的记忆。“Maya 带爸妈去的那家”和原帖“爸妈来看我，带他们吃了这家”几乎没有相同的词，关键词检索找不到；模型按语义相似度把它排到第一。
代码（确定性规则，不交给模型）：
- 权限与范围：朋友 / 自己 / 全部；他人私密、隐藏好友、未接受的申请都不进入候选；照片不参与计算。
- 硬条件：问题里点名的朋友必须是作者；“不要 / 除了”直接排除。
- 原帖不可能记录的条件（人均、营业时间、附近、适合几个人……）原样列为“原帖里没写，不做猜测”。
- 输出只有原帖 ID 和逐字引用的原文，经 validateModelResponse 校验后才渲染；卡片上展示的是朋友的原话，不生成任何新文字。
- 低于相似度阈值就说没找到；完全没有线索就追问一句。

4. 流程

打开“找那一餐” → 后台下载模型（标签显示“AI 模型加载中 xx%”）→ 就绪后预先计算可见记录的向量（标签“AI 检索 · 本机运行”）→ 用户提交 → recallPlan 做权限与硬条件 → 模型给问题编码，与每条候选的各字段向量比较 → 规则命中加分 → 阈值筛选 → 引用原文作为证据 → 校验 → 按餐厅聚合显示，右上角显示真实本机耗时（通常 20–50 毫秒）。
模型加载失败时提示可重试，或由用户主动选择“改用关键词检索”，结果标“仅关键词匹配，未使用 AI”。

5. 阈值（scripts/semantic-calibrate.mjs，在演示数据上校准）

minScore 0.46；margin 0.05（只保留接近最佳的结果，不凑数）；规则命中加 0.12；只有部分规则命中时仍需相似度 ≥ 0.42。

6. 边界

- 这是检索模型，不是生成式大模型：只排序和引用已有原帖，不写回答、不推荐新店、不编造店名地址价格。
- 中文效果好于英文；只理解文字，不看照片。
- 首次使用要下载约 37 MB（模型 24 MB + 运行时 13.5 MB），之后浏览器缓存。
- 阈值来自演示数据，不代表大规模数据上的效果。
- 演示没有账号，可见性过滤是前端演示规则；正式产品需要服务端鉴权，也可以在服务端运行同一模型或换成大模型。

7. 测试

npm test：28 项。tests/recall-semantic.test.mjs 在 Node 中加载同一个真实模型：7 条换说法的查询把正确原帖排第一；无关问题返回空；作者、否定、“适合两个人”等硬条件保持；朋友范围不返回自己的记录。
浏览器端到端（Chromium，按 /s/<appId>/ 子路径提供 site/）：模型约 2.4 秒就绪，DATA-MODEL.txt 第四节的主链路、聚合与边界查询结果全部符合预期。
