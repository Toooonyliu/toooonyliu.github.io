01

Research · Understand what I need

A skill was a starting point.
I still needed a speech engine.

I wanted to turn recorded classes and discussions into context for my AI agents. My first question was whether an existing free skill could do the transcription.

I asked the agents to inspect the tools behind those skills: what runs locally, what calls a paid API, and what would still need to be built for a website.

02

Prototype · Get one real file through

The first local attempt crashed.
That gave us something concrete to debug.

WhisperX is an open-source tool that transcribes speech and aligns words with their timing. I tried it locally before choosing the online setup.

On my Intel Mac, the latest dependency stack did not fit the hardware. After the agents found compatible versions, loading the model still crashed.

They compared the speech engine running alone with the same engine running alongside PyTorch. That isolated a conflict between two parallel-processing runtimes.

My next decision

Use a hosted engine for the public site.

The local test showed that transcription could work. For the website, I chose Deepgram Nova-3 so I would not need to maintain a model server. The tradeoff is usage-based API cost, plus hosting and storage.

I asked the agents to turn the local experiment into a working web flow. They helped separate the interface, the server endpoint, and the transcription service.

A deployment detail mattered.

The frontend needed its Deepgram provider setting at build time. Claude identified that configuration and carried it into the Vercel deployment. Afterward, the live site was checked with a real upload.

See the build settingVITE_TRANSCRIPTION_PROVIDER=deepgram

The API key stays in server-side environment variables.

04

Design & revise · Make the result useful

Getting text back was only
the beginning.

In-person playtesting reinforced the need to check the transcript before sharing it with AI. People wanted to see who said what, when they said it, and where the text might be wrong.

Feedback → interface decision

  1. 1
    Who said it?

    Stable speaker colors and clear turns.

  2. 2
    When was it said?

    A timestamp beside each paragraph.

  3. 3
    Does the text sound right?

    Replay and edit in the same view.

My review → the agents’ changes

Make the next action easier to find.

Send to AI was buried in a menu.
I asked Codex to move it into the recording header.
A project could become a very long paste.
I asked for an included-recordings list, one Markdown attachment, and a separate prompt.
Audio could disappear after a refresh.
Claude added browser storage so people could keep checking the original recording.

The handoff still requires pasting text or attaching a file in your AI chat. It is not an account connection.

05

Evaluate · Separate evidence from assumptions

Test the whole workflow.
Keep the remaining questions visible.

✓ VERIFIED IN THE PROJECT

  • Real backend: a live 90-second upload returned two speaker labels and supported click-to-play.
  • Review continuity: audio remained playable after refreshing.
  • AI handoff: Markdown download and prompt copying worked; ten synthetic transcripts stayed in order in a combined export.

↗ STILL TO TEST

  • Long recordings: the live large-file route and a full class session.
  • Correction quality: which word and speaker errors people find and fix.
  • AI usefulness: how well several long sessions support the next conversation.

What changed in how I work with AI

A concrete test made the collaboration useful.

I turned a broad goal into a specific check: upload a recording, replay a line, and correct its text. That gave the agents a problem to investigate and gave me a result I could judge.

AI helped me understand unfamiliar tools and implement the pieces. Choosing the workflow, noticing confusing interactions, and evaluating the experience with people stayed with me.
